1. Objeto y Alcance

1.1. Objeto del Documento

Presentar de forma clara y formal el procedimiento técnico para asegurar la estabilidad del servidor ante picos de tráfico en tiempo real (Plan de Mitigación) y realizar la población inicial de datos de inventario y seguridad en la base de datos Supabase en la nube para el aplicativo MIKITECH E-Commerce.

1.2. Alcance del Documento

Este documento abarca:

  • La ejecución de pruebas de estrés y mitigación de sockets mediante k6.
  • Los scripts de siembra en Python (seeding de productos, categorías y usuarios de prueba).
  • Las tareas de importación del catálogo inicial a través de hojas de cálculo de Microsoft Excel.

2. Participantes y Roles

Para la ejecución de los planes descritos se requiere personal técnico con acceso administrador a la consola del servidor local y al gestor de la base de datos PostgreSQL de Supabase en la nube.

3.0. Entorno y Preparación de la Prueba de Mitigación

Para garantizar que el sistema MIKITECH se evalúe bajo condiciones reales y controladas sin afectar la experiencia de clientes activos, el entorno objetivo de las pruebas será estrictamente el Entorno de Pruebas (Staging), el cual refleja de forma idéntica la configuración de red y la base de datos PostgreSQL de producción.

Previo a la ejecución de cualquier prueba de mitigación o estrés, el analista de control de calidad debe verificar la disponibilidad de los siguientes endpoints críticos del backend:

  • GET /api/products - Disponibilidad y tiempo de lectura de productos en inventario.
  • POST /api/orders - Disponibilidad del controlador de registro de transacciones de compra.
  • POST /api/auth/login - Disponibilidad del servicio de autenticación y generación de tokens de Supabase Auth.

⚠️ Verificación Obligatoria de Entorno: Compruebe en el archivo .env que los tokens apuntan a los buckets de almacenamiento y credenciales del esquema de Staging. Nunca inicie pruebas de carga activa si el backend está direccionado al entorno productivo.

3. Plan de Mitigación (Tráfico y Concurrencia)

3.1. Análisis y Diseño de Mitigación

Ante sobrecargas de peticiones en el servidor monohilo de Django, se detectaron caídas físicas de sockets. Se configuró un plan de contención de tráfico para asegurar que el sistema se estabilice automáticamente tras recibir picos inesperados de usuarios virtuales.

Configuración de la simulación de mitigación: Se escala instantáneamente a 60 usuarios virtuales (VUs), y en menos de 20 segundos se reduce y estabiliza a 20 usuarios residuales, analizando que la velocidad de procesamiento del servidor retorne a valores de latencia normales.

3.2. Procedimiento de Ejecución y Métricas Clave

Antes de iniciar la prueba de carga de k6, el analista de QA debe ejecutar la prueba de humo del sistema para certificar que el endpoint y la red responden de forma correcta bajo una carga de 1 único usuario virtual (1 VU):

k6 run tests/k6/smoke_test.js

Si la prueba de humo se ejecuta satisfactoriamente (tasa de éxito del 100%), se procede a correr el test de mitigación principal mediante el siguiente comando en la consola de comandos de PowerShell:

k6 run tests/k6/k6_mitigation.js

Durante la ejecución de la prueba, además de la latencia media y máxima reportada por k6 en la consola, se monitoreará el estado del servidor a través de las métricas clave de hardware y base de datos:

  • Uso de CPU (CPU usage) y Memoria RAM (Memory usage): Validar que no superen el 85% de capacidad para evitar bloqueos del sistema operativo.
  • Conexiones Activas a la Base de Datos: Vigilar en el panel de Supabase que el pooler de PostgreSQL (`6543`) amortigüe la carga sin sobrepasar las conexiones concurrentes permitidas.
  • Ratio de Errores HTTP (`http_req_failed`): Monitorear la salida de k6 en tiempo real. Para considerar la prueba como exitosa, el ratio de fallos final debe ser menor al **1%** (`rate < 0.01`).

3.3. Plan de Vuelta Atrás (Rollback)

En caso de bloqueo total del servicio local o falla en la conexión debido a saturación física de puertos TCP/IP:

  • Matar forzosamente el proceso del intérprete Python en la consola local: Stop-Process -Name "python" -Force.
  • Limpiar la tabla de puertos y reiniciar el servidor en producción Waitress utilizando 20 hilos concurrentes: waitress-serve --port=8000 --threads=20 mickytech.wsgi:application.

3.4. Registro y Análisis de Resultados

Una vez concluido el tiempo establecido de la prueba de mitigación (60 segundos), el analista de QA ejecutará el comando de exportación automatizada de k6 para generar un informe dinámico en formato HTML que consolide los datos de rendimiento:

k6 run --out html=reporte_mitigacion.html tests/k6/k6_mitigation.js

Los resultados de latencia, transacciones por segundo (RPS) y ratio de errores obtenidos de dicho reporte se anexarán al final de este documento técnico en un informe ejecutivo oficial que será evaluado por el líder de infraestructura.

4. Plan de Carga Inicial de Datos

4.1. Componente de Carga de Datos Origen

El cargue utiliza scripts independientes programados en Python que leen las variables de entorno de la base de datos PostgreSQL de Supabase en la nube para inyectar datos estructurados en lote.

4.2. Proceso de Carga Inicial Paso a Paso

⚠️ ADVERTENCIA DE SEGURIDAD: Todos los scripts de población de base de datos descritos abajo deben ejecutarse única y exclusivamente sobre el entorno de Desarrollo Local o Pruebas (Staging). Queda estrictamente prohibido apuntar scripts de seeding hacia la base de datos productiva sin la autorización explícita y escrita del Líder de Infraestructura.

Siga secuencialmente las instrucciones del terminal para realizar el aprovisionamiento de datos iniciales en la base de datos:

  • Paso 1: Ejecutar Migraciones. Crea las tablas lógicas en el esquema PostgreSQL de Supabase:
    .venv\Scripts\python.exe servidor-y-logica/manage.py migrate
  • Paso 2: Siembra de Datos Maestros. Registra categorías, 107 productos tecnológicos de catálogo, reseñas, likes e interacciones de usuarios de prueba:
    .venv\Scripts\python.exe scripts/database/seed_completo.py
  • Paso 3: Carga de Pedidos e Historial. Crea 10 ventas de prueba en base de datos para probar la consolidación financiera del panel de control:
    .venv\Scripts\python.exe scripts/seed_test_orders.py
  • Paso 4: Generación de Excel para Carga Masiva. Genera un archivo con 40 productos válidos para probar la importación masiva por archivo Excel del administrador:
    .venv\Scripts\python.exe scripts/generar_40_productos.py

✓ Confirmación Exitosa: Al ejecutar el proceso, podrás ver la consolidación en el panel administrativo de Django o en el dashboard del cliente con datos en vivo directamente desde la API en la nube.

6. Riesgos y Contingencias Adicionales

Riesgo 1: Fallo de Conexión a Supabase durante el Seeding de Datos

Impacto: Alto. La base de datos queda incompletamente poblada impidiendo las pruebas de negocio.

Plan de Contingencia: Reintentar automáticamente la ejecución del script de seeding configurando un temporizador (timeout) de 30 segundos entre cada intento. Si tras tres intentos consecutivos la conexión sigue siendo rechazada, abortar el proceso y notificar inmediatamente al líder de infraestructura para revisar el estado del clúster de base de datos.

Riesgo 2: Corrupción de Datos en Staging durante la Carga Masiva de Excel

Impacto: Crítico. Inyección de datos mal formateados, duplicidades o caída de la integridad referencial en las tablas lógicas.

Plan de Contingencia: Detener la carga y ejecutar de inmediato el comando de vaciado de tablas en Django para limpiar las áreas afectadas:

.venv\Scripts\python.exe servidor-y-logica/manage.py flush --no-input

Una vez limpiadas las tablas, proceder a restaurar el backup del esquema de Staging desde la última instantánea (snapshot) almacenada en la consola de administración de Supabase.
